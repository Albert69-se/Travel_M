# Travel-M source audit and implementation plan — 24 October 2026

## Objective

Keep the course prototype coherent with the M2 SRS, fix confirmed data-integrity
issues, and offer usable maps without relying on Google Cloud billing.

## Baseline

- `Albert69-se/Travel_M` is a vanilla HTML/CSS/ES-module implementation.
- The Mac checkout has previously uncommitted map, UI, README, and test work.
  Preserve those changes; do not reset, force-push, or deploy the unrelated React
  build from this repository.
- `node --test` initially passed 46/46 tests. Passing tests do not establish
  backend security, map accuracy, browser compatibility, or production readiness.
- The currently deployed VPS React app is a separate compiled application.

## Confirmed issues and work plan

1. Date validation accepted calendar rollover (e.g. 2026-02-30), contrary to NFR-5.
   Replace permissive parsing with a strict UTC date round trip and test leap days.
2. Expenses of positive amounts under half a cent could round to zero, contrary
   to FR-9. Reject sub-cent positive expenses that are zero when persisted.
3. Leaflet's CDN tags lacked Subresource Integrity. Pin the file bytes with
   SHA-384 hashes; retain an offline/unavailable fallback.
4. Google Maps JavaScript and Embed APIs require GCP setup; Google Maps URLs
   need no key. Keep Leaflet/OSM as the in-app map and provide Google Maps
   search/directions links from place details and marker popups.
5. Some UI mutation handlers did not ensure an active owned trip. Add guards to
   reduce accidental edits to another local account's records; do not claim
   that localStorage can deliver genuine production isolation.
6. Distinguish verified attraction information from samples; never imply that
   missing provenance is a confirmed fact.

## Acceptance criteria

- Existing tests remain green; new tests cover all fixes.
- No new production dependencies, secrets, paid APIs, or database migrations.
- No destructive action on existing browser data, local dirty checkout, or VPS.
- Google Maps is launched only by explicit user action using official keyless
  Maps URLs. Interactive in-page maps are clearly attributed to OpenStreetMap.
- Published GitHub source and live VPS React app remain unchanged unless a
  separate reviewed and authorized deployment path becomes available.

## Remaining architectural gaps

- Browser-local account data is not server-authoritative security or cross-device
  persistence (NFR-4/NFR-6). A backend and safe data migration are a separate
  project phase.
- Attraction facts and sample prices require independent evidence, not just
  coordinates on an OSM map (FR-3/NFR-9).
- Browser/UI and mobile tests, weather provider contract tests, 50-user load
  tests, and a reproducible deployment pipeline are still required.
- The M2 SRS refers to booking references in some NFRs even though bookings
  are out of MVP scope; reconcile in the next requirements review.

## Implemented locally (not yet pushed or deployed)

- Strict UTC calendar-date validation (including rollover and leap-year tests).
- Reject fractional-cent expenses which would round to a stored zero.
- Add a reference-place selection on new/edited trips; preserve the reference ID
  and fall back to an itinerary-linked place for weather if needed.
- Guard UI mutations against changing items outside the active owned trip.
- Distinguish reviewed/unverified place information from explicitly approved
  source-dated records in the interface.
- Report failed localStorage writes instead of claiming data was saved.
- Add SRI attributes for Leaflet 1.9.4 scripts/styles.
- Add optional Google Maps JavaScript adapter, automatic Leaflet fallback,
  and keyless Google Maps viewing/directions URLs. The user-supplied **demo**
  key is stored only in gitignored `js/maps-config.local.json` in this
  Mac working copy; it is not committed in Git.
- Update README with demo-key limitations, HTTP referrer/API restrictions
  and keyless fallback.
